# river3d — the River3 sensor

Observes `openat` / `execve` / `connect` for **enrolled workloads only** and emits one
typed `Event` per operation (Channel A facts, Channel B payload kept apart). Three
sources, one event shape:

| Source | Where it runs | How it identifies the workload | When the event is taken |
|---|---|---|---|
| `-source ebpf` | Linux amd64, root (the lab host, or inside the podman machine VM) | mount-namespace inode of the process, mapped through enrollment | syscall exit: outcome is the kernel's return value |
| `-source lsm` | Linux amd64, root, kernel with the `bpf` LSM active | same | BPF-LSM hook, **before** the operation: outcome is the sensor's decision (`success` = allowed, `blocked` = denied with `-block-decoys`); falls back to `ebpf` when the kernel cannot run LSM programs |
| `-source falco` | anywhere Falco runs (the Mac: Falco inside the VM, `river3d` beside it or on the host) | `container.full_id` / `container.id` from the alert, matched to enrollment | Falco's syscall exit |

Everything downstream — the containment controller, the API, the console — sees the
same JSON either way.

## Run

```sh
# build (linux/amd64 for ebpf; darwin/arm64 builds the falco path)
go build -o river3d .

# enroll: which containers matter (full 64-hex ids; pid/mntns are lab shortcuts)
cat examples/enroll.json

# eBPF, sending to the containment controller and the API
export RIVER3_SENSOR_TOKEN=dev-sensor-token RIVER3_INGEST_TOKEN=dev-sensor-token
sudo -E ./river3d -source ebpf -enroll enroll.json \
     -controller http://127.0.0.1:8787 -api http://127.0.0.1:8000

# BPF-LSM with inline blocking of each workload's decoys, enrolling labelled docker containers
sudo -E ./river3d -source lsm -block-decoys -shadow-profiles ../policy/examples/profiles \
     -enroll "" -enroll-from-labels -runtime docker \
     -controller http://127.0.0.1:8787 -api http://127.0.0.1:8000

# runtime discovery (contract §5) plus hostname resolution for egress-by-name rules (§4)
docker run -d --name worker-01 \
       --label river3.workload=worker-01 --label river3.profile=diagnostic-worker \
       --label river3.kind=ai_worker my-org/diagnostic-agent:1.4
sudo -E ./river3d -source ebpf -enroll "" -discover docker \
     -shadow-profiles ../policy/examples/profiles -resolve-hosts \
     -controller http://127.0.0.1:8787 -api http://127.0.0.1:8000

# Falco (Mac): Falco runs in the VM with falco/river3_rules.yaml and json_output=true
falco -r falco/river3_rules.yaml -o json_output=true -o priority=debug \
      -o http_output.enabled=true -o http_output.url=http://<river3d host>:8788/falco
./river3d -source falco -enroll enroll.json -falco-input "" -falco-listen 0.0.0.0:8788 \
          -controller http://127.0.0.1:8787

# replay a saved Falco stream, and see what the engine would say (shadow only)
./river3d -source falco -enroll examples/enroll.json -falco-input examples/falco_alerts.jsonl \
          -stdout -shadow-profiles ../policy/examples/profiles
```

Tokens come from the environment only. `RIVER3_SENSOR_TOKEN` must hash to a sensor
entry in the controller's registry; `RIVER3_INGEST_TOKEN` is an API principal with
role `sensor`.

## LSM source and inline blocking

`-source lsm` attaches `lsm/file_open`, `lsm/bprm_check_security` and
`lsm/socket_connect` from the same object file as the tracepoints. The hooks run in
the calling task, before the operation, and only for tasks whose mount namespace is
in `watched`, so the cost to the rest of the host is one hash lookup per call.

**Paths come from the kernel.** `bpf_d_path(&file->f_path)` renders the opened or
executed file relative to the caller's root with every symlink already followed by
the VFS, so `path_resolved` is true by construction and the userspace race of the
tracepoint source (process gone before `/proc/<pid>/root` could be walked) does not
exist. If `bpf_d_path` fails (a path over 255 bytes) the event carries no path; the
decoder then names the file from the blocked-inode table when it is one of ours and
otherwise leaves it unnamed rather than guessed. The program also records the file's
`(dev, ino)` in the kernel's own `dev_t` encoding (12-bit major above 20-bit minor);
`inodes.go` converts `stat(2)`'s `st_dev` to that encoding, and
`TestKernelDevMatchesMountinfo` checks the conversion against the running kernel's
`mountinfo`.

**Outcome semantics.** An LSM event is marked `"inline": true`. Its outcome is the
sensor's decision: `success` when the hook allowed the operation, `blocked` (with
`errno: 1`) when it returned `-EPERM`. Three consequences worth knowing:

- a `net_connect` that the hook allowed is `success` even if TCP later fails or the
  socket is non-blocking (the tracepoint source would say `pending` / `failed`);
- a `process_exec` is reported for the file the kernel is about to run
  (`python3.13`, not the `python3` symlink), before the image switch, so
  `process.comm` is still the caller's and there is no `argv` (Channel B is empty);
  a script exec yields one event per binfmt stage (the script, then its interpreter);
- the content hash is taken from `/proc/<pid>/root/<exe>`, the file the kernel
  named, since `/proc/<pid>/exe` is still the parent at that point.

**`-block-decoys`.** At every enrollment refresh the sensor resolves each watched
workload's profile `decoys` and `protected_read` patterns inside
`/proc/<init pid>/root` (literal paths, `*` within a segment, trailing `/**` for a
subtree including the directory itself; at most 4096 inodes and 2 s per refresh) and
writes `(mntns, dev, ino)` keys into the `blocked_inodes` map **before** the
namespace is added to `watched`, so there is no window in which a decoy open is
observed but allowed. The hook denies every open of a listed inode, whatever the
flags, and emits the `blocked` event; the decision is computed before the ring
buffer is touched, so a full buffer can lose the record but never the denial.
Inodes, not paths: a hard link, bind mount or rename of the decoy still hits the
same inode. The mount namespace in the key keeps one workload's decoy from blocking
the identical lower-layer inode in another container of the same image. A decoy
created after enrollment is covered at the next refresh. The profile comes from
`-shadow-profiles DIR` (the `-profiles-from-api` bundle is not implemented here);
without it `-block-decoys` is an error, and a workload whose profile name is not in
the directory is logged once and not blocked.

**Fallback.** Before loading, the sensor reads `/sys/kernel/security/lsm`: a kernel
built with `CONFIG_BPF_LSM` but booted without `lsm=…,bpf` loads and attaches LSM
programs without error and simply never calls them, which an enforcement sensor must
not mistake for success. If `bpf` is absent, the hooks have no BTF, or the kernel
refuses to load the programs, `-source lsm` logs a warning and continues as
`-source ebpf` (contract §8). With `-block-decoys` it refuses to start instead:
silently not enforcing is worse than not running. A verifier rejection is reported
as such and is not a fallback case.

## Discovery by labels

`-enroll-from-labels -runtime docker|podman` lists running containers with
`river3.enroll=true` (`GET /containers/json?filters={"label":[…]}`; libpod routes
for podman) every `-refresh`, reads the labels from the runtime's own database (a
workload cannot relabel itself) and applies the same validation as the `-enroll`
file:

| Label | Required | Notes |
|---|---|---|
| `river3.enroll` | yes | must be `true` |
| `river3.asset_id` | yes | identifier (`^[A-Za-z0-9][A-Za-z0-9_.:-]{0,127}$`) |
| `river3.profile` | yes | profile name |
| `river3.kind` | yes | `ai_worker` or `shared_service` |
| `river3.name` | no | defaults to the container name, then the asset id |
| `river3.team` | no | ≤ 64 chars; forwarded as `team` on the workload reference and in the API registration |
| `river3.dedicated`, `river3.actions` | ignored | the controller's concern (§4.1) |

The identity binding is unchanged: the container id from the listing is resolved to
the init PID through the runtime and to a mount namespace through `/proc`; labels
never reach the kernel map. The `-enroll` file is merged in and **wins every
conflict** (same `asset_id` or same `container_id`), so an explicit enrollment cannot
be hijacked by a label; a duplicated label `asset_id` keeps the first container by
id. A container with bad labels is logged and skipped while the others enrol. If the
runtime socket fails, the previous discovery result stands (nothing is unwatched by a
hiccup); a container that disappears from the listing is unwatched at that refresh.
Workloads are registered with the API (`POST /api/v1/workloads`, with `team` when
set) the first time they are seen and again when their descriptive fields change.
The runtime client is created only when something needs it: the Falco source with a
plain enrollment file no longer touches the podman socket.

## Runtime discovery (`-discover`, contract §5)

`-discover docker|podman` enrols every running container that carries these labels,
read through the Docker-compatible Engine API on the runtime's unix socket
(`-runtime-socket`, default `/var/run/docker.sock` for docker and
`/run/podman/podman.sock` for podman):

| Label | Required | Notes |
|---|---|---|
| `river3.workload` | yes | the asset id: identifier (`^[A-Za-z0-9][A-Za-z0-9_.:-]{0,127}$`) |
| `river3.profile` | yes | profile name (same identifier rule) |
| `river3.kind` | yes | `ai_worker` or `shared_service` |
| `river3.name` | no | defaults to the container name, then the asset id |
| `river3.team` | no | ≤ 64 chars; forwarded as `team` |

```sh
docker run -d --label river3.workload=worker-01 --label river3.profile=diagnostic-worker \
       --label river3.kind=ai_worker my-org/diagnostic-agent:1.4
podman run -d --label river3.workload=svc-b --label river3.profile=payment-service \
       --label river3.kind=shared_service --label river3.team=payments my-org/payments:2.0
```

How it works, and what it does not do:

- **One API, two runtimes.** Docker serves the Engine API unprefixed; podman serves
  the same compat API under a version prefix (`/v4.0.0/...`) and unprefixed. The
  client probes `GET <prefix>/_ping` once (podman: `/v4.0.0` then bare; docker: bare
  then `/v1.41`) and remembers the answer; a daemon that is down is probed again at
  the next refresh. `-enroll-from-labels` with `-runtime podman` still uses the libpod
  routes as before.
- **Listing** is `GET /containers/json?filters={"label":["river3.workload"]}`; only
  `running` containers with a full 64-hex id are considered. Each becomes an
  `Enrollment` with that id, and the init PID comes from `GET /containers/{id}/json`
  → `.State.Pid` exactly as for the `-enroll` file, so identity is still the mount
  namespace the sensor itself resolves. Labels are read from the runtime's database,
  never from inside the container.
- **Validation** is the enrollment file's: a container with a missing or malformed
  label is skipped and logged **once** (again if its labels change and are still
  wrong, or if they are fixed and then broken again); the others still enrol.
- **Merge.** The `-enroll` file wins every conflict on `asset_id` or `container_id`
  (logged); among discovered containers the first by container id keeps a duplicated
  asset id; `-enroll-from-labels` results, when both are on, take precedence over
  `-discover` for the same container. The total is bounded at **1024** enrollments;
  discovered entries beyond that are dropped and the count logged, file entries never.
- **Refresh triggers.** The listing is repeated every `-refresh`, and the sensor also
  follows `GET /events?filters={"type":["container"],"event":["start","die","stop","pause","unpause"]}`:
  any event asks the enroller for an immediate refresh (kicks coalesce; at least
  250 ms apart). The stream reconnects with backoff (1 s doubling to 30 s) and the
  periodic refresh never waits on it, so a runtime without `/events` just works at
  `-refresh` granularity. A runtime outage keeps the previous discovery result (no
  container is unwatched by a hiccup); a container gone from the listing is unwatched
  at that refresh.
- **Registration.** Discovered workloads are registered with the API like file ones
  (`POST /api/v1/workloads`, `sensor: "ebpf"`) with
  `labels: {"discovered": "docker"|"podman"}` so the console can tell them apart.
- **Trust.** Allowing discovery is a decision about whoever can start labelled
  containers on that host: a label claims an asset id and a profile, nothing more, and
  cannot override a file enrollment.

## Hostname resolution (`-resolve-hosts`, contract §4)

Profiles may allow egress by name (`"api.openai.com:443"`). The kernel reports IPs, so
the sensor resolves the names itself: every hostname in the loaded profiles'
`egress_allowed` (parsed with the policy package's own grammar, `Profile.EgressHosts`)
and `egress_allowed_domains`, plus the names in `-hosts-file`, is looked up with
`net.Resolver` every `-resolve-every`, and the answers fill an **IP → host cache**. A
`net_connect` whose destination IP is in the cache carries
`facts.target.host` (`Target.Host`, `omitempty`); the in-process shadow path sets
`Event.DestHost` and `Event.Port` from it, and the containment controller will copy
`target.host` to `DestHost` when its side lands. The Falco source fills the same
field from `fd.rip`.

Limits and semantics, deliberately:

- **≤ 256 names** (sorted; the excess is logged and not resolved), **8 lookups in
  flight**, **2 s per lookup**; a round never blocks the event path (the first round
  runs in the background).
- **TTL.** An entry expires `-host-ttl` (10 min) after the round that last confirmed
  it. A name that stops resolving keeps its last addresses until then and is logged
  once (and once more when it resolves again). An address claimed by two names goes
  to the first in sorted order within a round.
- **Wildcards cannot be resolved.** `*.github.com` has no forward resolution; it is
  logged once and skipped, and a connect to a GitHub address carries no host.
  Matching wildcard rules needs a sensor that observes the workload's own DNS
  answers; that is planned and is not this.
- **It is the operator's resolution, not the workload's.** Split-horizon DNS, a
  CDN rotating addresses faster than `-resolve-every`, or a poisoned resolver inside
  the container all produce connects to IPs the cache does not know; the event then
  has no host, and a hostname-only rule leaves it `EGRESS_OUTSIDE_SCOPE` with
  `host_unknown`. That is the fail-safe direction; it is also why the cache only
  ever makes an IP *more* legible and never suppresses an event.
- Only names of the shape the engine accepts for `DestHost` (lowercase, two or more
  labels, non-numeric last label, no wildcard, no IP literal) are resolved, so a
  cached host can never make the engine reject the event.

## Trust notes

- **Identity** is the mount namespace the kernel reports, matched to a namespace the
  sensor itself looked up for an enrolled container id. Nothing a workload can set
  (labels, env, hostname) participates. A restarted container gets a new namespace;
  the enroller re-resolves every `-refresh` and swaps the map entry.
- **Paths**: the string passed to `openat` is resolved component by component under
  `/proc/<pid>/root` (and `/proc/<pid>/cwd` for relative paths), with absolute
  symlink targets re-rooted at the process root — what the kernel did for that
  process. `path_resolved: true` means this succeeded. It is a userspace read after
  the syscall, so a rename in between can defeat it; the containment controller
  treats it as evidence, not as filesystem authorization.
- **Executables**: on a successful exec the file is confirmed by device+inode against
  `/proc/<pid>/exe`, so a `python3 → python3.13` symlink or a relative name resolves
  to the real binary. The class then comes from the file's content, not its name
  (see *Binary identity*); the controller trusts it when `exe_sha256` is present and
  falls back to its own name table otherwise.
- **Outcome** is the syscall return: `success`, `failed` (+`errno`), `pending`
  (`EINPROGRESS` on a non-blocking connect). Events are emitted on exit, never on
  entry, so every event has one. Inline (LSM) events add `blocked`: the sensor's own
  denial, never the kernel's verdict; downstream treats it as failed-class (§9).
- **Inline events** (`"inline": true`) are the sensor's decision taken before the
  operation. Their paths are the kernel's (`bpf_d_path`), not a userspace walk.
  Blocking is by inode and is only as current as the last refresh.
- **Labels** are read from the runtime, never from the container, and never decide
  identity; they only say which asset id and profile a container claims, and the
  `-enroll` file overrides them. Allowing label enrollment is a trust decision about
  whoever can start labelled containers on that host.
- **Timestamps**: `t_kernel_*_ns` are `CLOCK_MONOTONIC`; `t_received_ns` is wall
  clock computed from the boot offset at startup. Falco events carry `evt.rawtime`
  in both.
- **Falco path**: `fd.name` / `proc.exepath` are already resolved by libsinsp and are
  marked resolved; the raw filename of a failed open is not. Only `river3_*` rules are
  mapped. `proc.cmdline` is split on whitespace for Channel B only.

## Binary identity

A name is not evidence: `cp /usr/bin/curl /tmp/python3 && /tmp/python3 …` would be
an INTERPRETER by name. On every successful exec the eBPF source hashes the file that
is actually running (`sha256` of `/proc/<pid>/exe`, which follows to the inode even
when the file was deleted) and looks the hash up in a table of the workload's own
image binaries. The table is built from `/proc/<init pid>/root` under `/usr/bin`,
`/usr/sbin`, `/bin`, `/sbin`, `/usr/local/bin`, `/usr/local/sbin` (in that order; the
first directory to hold a given content names it, so `/usr/bin` wins over an alias in
`/bin`). Symlinks are resolved inside the root only, and the image's own aliases
(`sh → dash`, `python3 → python3.12`) are kept so an exec through one of them is not
mistaken for a rename. Tables are keyed by mount namespace and rebuilt in the
background only when a workload's namespace changes (restart) or every 10 minutes.

Four outcomes, all legible in `binary_detail`:

| Evidence | `binary_class` | `binary_detail` | flags |
|---|---|---|---|
| hash in the image, same name | from the name, as before | as before (`NET_CLIENT`, `SHELL`, …) | |
| hash in the image, different name | from the **canonical** name (a copied curl stays `NET_CLIENT`) | `RENAMED:<canonical>` | `renamed: true` |
| hash not in the image (downloaded, compiled at runtime) | `OTHER` | `UNKNOWN_BINARY` | `foreign_binary: true` |
| no table yet / walk incomplete and no hit / file unreadable | from the name | `<detail>:NAME_ONLY` | |

Files above 64 MiB are not hashed: `exe_sha256` is empty, the detail ends in
`:UNHASHED`, the class is name-based, and the event is never delayed. Caps: 64 MiB per
file, 8192 entries and ~5 s of walking per workload (over either marks the table
`partial`, which turns "not found" into `NAME_ONLY` rather than `UNKNOWN_BINARY`),
and a 4096-entry LRU of hashes keyed by `(dev, ino, size, mtime)`. New event fields,
all `omitempty`: `exe_sha256`, `exe_dev`, `exe_ino`, `exe_size`, `renamed`,
`foreign_binary`. Failed execs and the Falco source carry none of them, so the
controller treats those exactly as before. A bare `mntns` enrollment has no root to
walk; its execs are `NAME_ONLY`.
